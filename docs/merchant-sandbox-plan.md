# 商店与义体服务沙盘化方案

日期：2026-11-17。状态：策划与源码核查完成，尚未实施。核查基线：`0439ebd`。

目标：原商店、义体、背包、地图和人物面板继续使用；按钮与自由输入操作同一份交易事实，商人和货物能随世界事件变化。正文表达仍交给预设。制作阶段直接替换废弃逻辑，不新增历史兼容层。

## 2. 玩法目标

保留随时自由输入。玩家可以询价、讲价、赊账、交换、代购、订货、卖赃物、自带义体安装，也可以偷抢、放弃交易或与店里另一人私下交易。代码检查持有权、承诺、资金和事实一致性；人物是否愿意接受，由已有关系、知情范围、利益与处境决定。

“我买下它”不能凭空产生卖方没有的货；“我想偷它”也不等于已经拿到。询问和报价不扣款，交付才转移归属。偷抢使用其实际行动结果和物件转移，不能伪装为免费购买。

不朽、军用或稀有标签不直接决定“永远不能交易”。可以作为初始货源罕见、受控或特殊来历的描述；已经有人实际持有且愿意转让时，按具体事实处理。黑市标签同样不自动触发故障、追踪器或惩罚。

## 3. 所有入口共用一次报价与成交核验

流程：确定交易对象与货源 → 取得当前报价 → 玩家接受明确条件 → 一次性核验并完成交付。

同一份报价应记录：卖方、买方、物件或服务、数量、币种与金额、交换物、赊欠条款、旧件处理、交付条件、来源证据，以及报价所依据的库存版本。只有约定了截止时间才记录到期，不给所有报价强加倒计时。

按钮读取当前货架报价；文字请求按同一个卖方、商品和条件取得同一报价。店外私人交易、自带零件和赠送也可创建有来源的交易条件，不要求必须在现有六家店购物。模型不能用任意 `price: 0` 覆盖货架价格；真实赠与需记录谁同意赠送什么，砍价需记录对方接受的新金额。

价格变化必须有可追溯依据，例如店主公布报价、实际谈判、缺货、货况或具体关系。不把抽象好感阈值或“这个城区有某帮派”自动变成每家店统一打折。初始价格表可以作为开局参考，商家自己的报价形成后持续保存。

普通买卖作为一笔交易原子执行：钱、货、库存、旧件和债务全部成功才生效；失败全部保持原样。重复提交同一交易不会重复扣款或给货。大额消费确认也使用这份报价，确认后条件发生变化就重新说明，不按新价格偷偷成交。

已有 `applyPlayerAction` 和单条命令的连锁回滚可复用。纯报价与核验函数同时供面板投影、判断阶段与执行阶段调用，避免各处再实现一遍。是否仍使用原指令名称属于实现细节，不保留两套交易语义。

特殊情况：在一处地点可以有多个商家；不能直接取第一家。仅姓名无法区分时，先以人物、店铺和物件上下文消歧；证据不足就留在询价阶段。先到店再购物应按事件先后核对到达后的地点，不能因为本轮包含出行就跳过库存校验。

## 4. 店铺和货物持续存在

每家经营场所保留少量实际状态：

| 状态 | 保存什么 | 不必做什么 |
| --- | --- | --- |
| 经营场所 | 稳定 ID、地点、类型、经营者、服务人员、当前营业情况及原因 | 不把一次打开面板当一次重新生成 |
| 商品 | 数量、实际持有人、货况、来源、已确认报价 | 普通同类商品可按批次计数，无须每瓶饮料单独建卡 |
| 特殊实物 | 唯一身份、改装、损伤、赃物来历、已知检测结果 | 不让同一把特殊武器同时出现在两个人手里 |
| 供货 | 谁供货、运什么、预计到达、受何事件影响、是否已完成 | 不模拟全城每辆货车的每分钟位置 |
| 订单和债务 | 谁欠谁、约定金额或物品、交付条件、完成情况 | 不把所有人统一设为只能欠一笔、必须七天还清 |

商品批次只是账目粒度；玩家改装、损坏或转赠某一件后，将它分离成具体实物。已卖给商家的装备继续存在，附着配件随明确约定处理，不能在卖出最后一把枪时悄悄删除配件。

地图保留完整地点索引，只有接近、访问、下单或受事件牵连的店铺需要展开详细状态。首次初始化可按已知原作资料、店铺类型和城区条件确定开局货源；初始化后保存一次，重访不重新抽货。固定内容表是世界初始条件，不是世界永久只准存在的清单。

同一实际店铺的地图 POI 和剧情地点通过经过核对的关联表连接；不靠名字相同或距离近就合并两家不同店。其他服务点可逐类补齐服务能力，不能把酒吧、诊所、出租设施都套成武器商店。

## 5. 补货与经营如何演变

首次备货建立初始库存。此后购买、售回、损坏、偷窃、供货到达都会改变现存数量。取消“过三天自动把所有品种补满”的运行逻辑；普通稳定补给可用已有供货关系建立周期订单，由游戏时间和路线状态本地推进，不必每次问模型。

例如：枪店已经向供货商订了弹药 → 预计周五送达 → 道路因已发生的封锁中断 → 该批货延迟 → 店主只能卖现货或接预订。封锁解除后按订单继续交付，不能一回店就忘掉缺货。

不强制每批货遇到麻烦。路线正常时照常到货，平静经营可以一直持续。只有相关事件才改变供应、报价和营业状态；不把每条全城新闻自动传播给所有商家。

明确死亡或不在场的医生不能本人接诊；诊所有其他合格人员时仍可营业。人物位置未知不等于已经离场，需区分“尚未记录”和“已确认不在”。同理，店主死亡不必自动永久关闭有员工经营的店。

商家也不能无限出钱收购任何东西。收购范围、是否愿意接货和大额支付能力属于商家事实；日常小额经营可用简洁经营资金记录，不扩展成全城会计系统。

## 6. 义体购买与手术分开

“拿到义体”“医生接受安装”“手术完成”是不同事实。玩家可以买了暂不装、携带捡来的义体检查、寄存、转卖，或选择另一位医生。自带义体按适配、货况、所需设备与服务报价处理，不再只存在于正文里。

手术前确认具体部位、设备、医生、报价和时间。需要替换时必须明确哪件旧义体被拆，以及旧件保留、卖回或报废的去向；没有授权就不能自动卖掉最早安装项。当前部位布局可继续显示，不借此重做义体面板。

简单服务可以在一次已确认行动中完成并推进相应游戏时间；预约、复杂手术或未满足条件的服务才保留订单。正文和代码使用同一开始/结束时间，避免抽取又推进一次；只有已确认会中断操作的事件才改变结果，不为戏剧性追加失败。

恢复情况按实际手术和已有伤势记录，不恢复“安装必扣人性”、升级门槛或固定神经惩罚。完整现实医疗仿真不在本案范围内。

## 7. 提示词与调用成本

- 打开货架、查看报价、普通按钮成交：本地计算，目标仍为 0 次模型调用。
- 自由输入询价、砍价、交换、威胁或订货：复用现有判断、正文、抽取主链，不额外固定增加“商人模型”。
- 判断阶段读取当前卖方、相关商品、已确认报价与实际条件；正文拿到同一报价和交易进度；抽取只登记已经接受并发生的变更。仅报价或计划不算交付。
- 正常到货、库存扣减、已知营业时段：代码按已保存事件推进。复杂供货谈判、事件导致的经营决策必要时并入既有场外推演，不按每家店新增独立请求。
- 上下文只带当前店、相关商人、正在讨论的货物、未完成订单及有关变化。查询整张货架可在原面板完成，不把全城所有货架塞进正文请求。
- 报价、店铺索引和供货基线使用确定性代码，模型负责人与局势的解释。按证据更新，不为了省 token 删除角色边界或未履行交易。

这些是调用结构目标，实际 token 和费用要在实施后用请求样本验证，当前不宣称具体节省比例。

## 8. 分批实施与验收

**第一批：统一六家已实现店铺的交易。**

统一报价、卖方身份、库存、余额、旧件与大额确认路径；让自然语言也能记录已谈妥条件。修正现有售卖配件丢失及义体店价不一致问题。先保留当前供货行为，交付说明它尚未沙盘化；不把中间步骤冒充完整经营系统。

验收：同条件按钮/文字同价、同物、同库存；换一种说法不能绕过货源；在店里向另一人购买不扣店铺库存；谈价未接受不扣钱；赊账及交易失败不产生半笔结算；存档载入、撤回和重复请求行为一致。

**第二批：持续店铺状态与地图关联。**

建立店铺身份、经营者和实际库存，清理废弃声望解锁字段。核对现有店铺与 POI 的关系；按商店类型逐类接入服装、食品、武器、义体等服务，未支持类别明确保留为地点，不假称所有服务点均已实现。首次展开后持久保存。

验收：地图和剧情入口看到同一家店、同一库存；重访不重置；两家同名店不误合并；明确缺席的服务者不能接单，未知位置不被误判关闭；故障恢复不会重复生成商家和货物。

**第三批：补货、订单与义体服务演变。**

替换固定补满逻辑，增加有来源的供货事件、订货、旧件保存、自带义体与安装服务时间。复用场外推演处理牵涉人物决策的变化。

验收：到货只执行一次；已封锁路线不能照常瞬间补货；无关新闻不使全城商店一起涨价；手术时间不重复累计；中断、取消和失败按已完成阶段处理，不能凭空退回已消耗或移走的实物。

每批独立提交，运行针对交易一致性和存档重放的测试、相关类型检查，并核对 `apps/web` 文件散列不变。当前前端还有人性预览旧文字，仅在本案列为后续内容问题；本轮不调整任何前端文件。

## 9. 本轮交付边界
