## 仍需完善的设计能力

这些不是“测试通过就解决了”的问题，也没有在本轮偷偷扩成新架构。

1. **缺少通用的因果依赖记录。** 当前跨命令只对部分支付、取货、战斗等关系有专门联动；还没有统一表达“这笔收益依赖这次开锁成功、这个消息依赖这次接触发生”的事件结构。本轮拦截的是“接入动作被实际拒绝且同批有收益”的确定路径；矛盾批次整体退回草稿，无法精确保留其中的独立收益。仅有阻断裁决、没有失败接入指令的独立还款仍可结算。因此抽取漏掉失败动作、只报收益的情况仍需通用依赖结构核验。下一阶段应设计带前置条件、结果与依赖的事件结算，允许确认独立的事件单独成功。
2. **车辆没有实际地点。** `OwnedVehicle` 记录型号、车况和归属，没有停放位置、当前驾驶车辆与送车过程，因此后备箱无法判断是否就在玩家身边。需要把车辆移动、召车和容器可达性一起建模，单加一个禁止按钮无法闭环。
3. **同型号普通物品仍主要按数量堆叠。** 独立物件有稳定身份，普通补给的余量却仍按型号记录，不能精确区分“同型号两包，哪包半用过、哪包转交或存进箱子”。NPC 装备也不能表示多件同款的数量。本轮保住不吞物，尚未将全部物品实例化。
4. **普通医疗等部分服务的付款和交付仍是不同指令。** 普通医疗服务付款与伤势治疗尚未统一为一个可跟踪订单，欠缺通用的交付状态、失败、退款与免费服务来源表达。义体手术已有专用订单状态，并非所有服务都没有交付记录。不能简单要求所有治疗都必须付钱，否则又会误伤救援和赠与。
5. **世界演变仍依靠选中的上下文与模型提议。** 已有持续状态、到期事项、场外批次和消息渠道，但不是全城每个人都具备独立计划、预算、行程与信息传播的完整模拟。部分参考价格、名声标签和固定内容仍在；“所有事物均从底层自然演变”的目标还没有完全实现。

后续优先级建议：先补事件因果与结算依赖，再补车辆位置和容器可达性，随后完善普通物品实例与服务交付；这些都可以沿用现有界面。

本轮没有使用真实付费模型，没有以真实连续游玩验证文笔。警戒改为按地点记录，NPC 新增玩家已知信息；遵循制作阶段不兼容的约定，没有旧结构迁移层。当前格式的保存/载入和失败恢复由回归测试覆盖。对 `apps/web` 的本轮 Git 差异为空，原有界面、布局、样式与展开面板没有修改。
