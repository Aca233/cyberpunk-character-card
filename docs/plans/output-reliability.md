# 提高模型输出成功率：实施方案

日期：2026-11-28。状态：首批可靠性修复及本轮上下文、调用边界修复已实施；验收和剩余范围见第 8–9 节，结构化输出与修复流程的 P1 尚未实施。

## 1. 目标与范围

本方案将“输出成功”理解为：玩家提交行动后，模型完整生成正文，事实按规则结算，回合可靠写入存档。只收到文字、HTTP 返回 200、流关闭或收到 `done`，都不能单独代表完整成功。

优先提高首次完整成功率和失败后的可恢复性，减少整轮重跑、重复计费与无限等待。保持静态前端架构，复用现有界面、阶段提示、草稿和断点交互。

约束：
- 正文质量优先。不靠缩短正文、删人物身份和知情边界、裁掉关键记忆或放松结算校验换取通过率。
- 用户写作预设继续控制文风、篇幅与节奏；辅助任务的格式约束不侵入正文创作。
- `refusal`、`content_filter`、安全拦截、空回复明确失败，不自动重试，不静默切换模型或服务商。
- 已完成的正文、已确定的裁决和已写入的状态不得因恢复而被暗中重算。
- 不新增独立后端、单元测试框架或旧 schema 兼容层；按已批准范围分批实施。

## 2. 改造前的实现与实际缺口

以下是实施前的代码审查快照，其中部分问题已由首批改动修复，具体见第 8 节。尚无真实模型失败样本统计，不能据此断言哪个原因占比最高或承诺提高到某个百分比。

### 已有保障，继续沿用

- 判断、正文、抽取分工；正文以纯文本流式生成，账目在后续独立抽取。
- `prepared / narrated / extracted` 三阶段断点，按存档版本和输入键恢复；抽取失败可以保留完整正文。
- 原生 JSON 模式、逐项 schema 校验、ID 归一、错误条目有限批量修复。
- 事件依赖与组内原子结算；独立事件可保留，关键账目不一致标为未定稿。
- 网络异常已有两次退避重发；SSE 已处理跨块中文、CR/LF、多行 data 和中断错误。
- requestId 查重、事件序号续收、提交前版本核对；日志成功后清断点或写快照失败不会误报回合未保存。
- 正文和抽取已有上下文预算保护；场外推演、摘要失败已有部分非致命处理。

### 优先处理的缺口

| 问题                     | 代码依据                                                                                                                                            | 对成功率或恢复的影响                                   |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 传输结束被补成自然完成   | `providers/openai.ts` 在缺少 finish reason 时把 `[DONE]` 补成 `stop`；`providers/anthropic.ts` 将缺少 stop reason 的 `message_stop` 补成 `end_turn` | 不完整结果存在被误判成功的路径                         |

| 恢复参数被冻结           | `prepared` 保存并复用 narrateMessages 和 maxOutputTokens                                                                                            | 改好设置后，重试可能仍沿用旧执行额度，生效规则不清晰   |
| 缺少完整成功口径         | 草稿也可能经 `kind: done` 提交；现有 eval 不经过真实 GameService 落盘                                                                               | 接口完成率或 eval 通过率不能直接代表完整回合成功率     |

## 3. 推荐改造

### A. 先统一“成功、截断、失败”的判定（P0）

在 provider 边界保留原始结束原因，统一区分自然完成、输出截断、安全拦截、空回复、协议缺失、网络错误和超时。只有明确自然完成且正文非空，才允许进入事实结算。
- `[DONE]` 和 `message_stop` 只表示传输结束，缺少明确完成原因时按不完整处理。
- Gemini 的截断与其他 provider 采用一致的上层处理路径：已有正文可保存草稿，不结算未完成正文。
- 中途断流同样保留已收到的可用正文；草稿与已完成的 `narrated` 断点严格区分，不能把半截正文当完整正文继续抽取。
- 增补 OpenAI / Anthropic 关键流事件字段校验，允许无关扩展字段，关键字段畸形时给出协议错误。
- 不必为此立即重构全部 SSE 事件。统计和界面状态需识别草稿、未定稿、完整结算，不能只看 `done`。

这部分首先修正假成功与恢复损失，报表通过率可能暂时下降，应与实际完成率分开评估。

### B. 为各阶段建立明确的请求预算（P0）

在 runtime 统一管理连接、首个有效生成事件、流空闲和阶段总时长。阈值按判断、正文、抽取、补充任务及模型配置区分，通过基线耗时校准。
- 原生 thought 或有效生成事件算模型仍在工作；仅 SSE 心跳不应无限延长等待。分别记录传输活动与有效生成活动。
- 超时使用独立错误类别，不能误显示为用户主动“已停止”。取消后应清理计时器、reader 和重试等待。
- 将已有预算保护补齐到判断、修复、场外推演、摘要；正文和抽取沿用现有保护，统一纳入协议包装余量和模型实际输出上限。
- 输出额度按任务规模分配，区分思考和可见正文的消耗；不默认调低用户思考强度或篇幅。
- 预算不足时在发送前明确说明哪一阶段、需要多少窗口或输出额度。正文已经完成则保留正文，只修复剩余阶段的配置。
- 补充推演和摘要仍保留现有非致命语义，增加有限等待；不能为了提交更快直接丢弃长期记忆任务，未完成任务须有明确状态和后续处理规则。

### C. 提高结构化输出的一次合格率（P1）

增加按连接端点和模型区分的能力描述：支持 schema、仅 JSON 模式，或仅提示词约束。能力来自用户明确配置、已知适配或显式验证；不按模型名猜，也不在游戏回合内悄悄付费探测。
- 支持时为判断、抽取和修复使用实际生效的 schema 约束。
- 抽取先约束必需字段、事件外壳、依赖列表和基本类型；业务指令继续由本地 registry/schema 严格验证。
- 不把庞大的指令全集直接塞入一个严格 union；先确认供应商可支持的 schema 子集，再评估按场景缩小候选指令。不能因为预判没激活某模块，就漏记正文实际发生的事实。
- schema、提示词说明和本地校验尽量共用同一来源，减少三处漂移。只有参数明确不支持时才允许显式配置兼容模式，不能在遇到安全拦截后降级绕过。
- JSON 解析先尝试完整内容，再识别完整围栏或理解字符串转义、括号配对的唯一完整对象；多个候选有歧义时明确失败。不补造缺失的业务字段，不拼接多份回复，不把截断 JSON 修成既成事实。

### D. 将修复改为针对错误的有限流程（P1）

推荐顺序：本地无损整理 → 外壳/事件图修复 → 关键条目批量修复 → 本地规则复核。
- 保留现有“合法条目不动、只修错误条目、关键账目优先”的原则。
- 外壳修复和关键条目修复拥有明确子额度，避免外壳消耗全部机会；外壳已修好时不再整份重写。
- 每次只携带出错片段、准确校验路径、必需 schema、合法 ID 候选及相关原文证据。不得让模型为过校验而改变金额、人物、时间、主行动结果或依赖关系。
- 输入、输出额度按错误规模和辅助窗口核算，无法容纳时明确保留待修项目，不无限拆批。
- 对自然完成、非空且未被拦截的抽取回复，可缓存原始候选和校验进度；重试优先继续定向修复，避免重新抽取整篇正文。
- 设置“修复调用数、技术重试数、总 token、总时间”联合上限；预算跨断点恢复累计，不能每次续跑就自动刷新。用户主动开启新的尝试时明确重新计数。

第一版可以先允许一次外壳修复加一次关键条目批修，具体上限依据基线和费用调整，不能演化为递归自修循环。

### E. 只对合适的技术错误进行有限重试（P1）

收拢当前 HTTP 重发与 direct/proxy 切换，统一统计实际 HTTP 尝试次数，避免叠加后请求数失控。`retryable` 表示可以再次尝试，不等于安全自动重发。

| 情况                                                | 默认策略                                                                         |
| --------------------------------------------------- | -------------------------------------------------------------------------------- |
| 明确临时限流、明确未接单的临时不可用                | 无正文且仍在预算内时有限退避，尊重 Retry-After，加入抖动                         |
| 网络异常、网关超时，无法确定上游是否已接单          | 标明结果不确定，默认由用户决定重试；供应商支持幂等键时才利用其保证               |
| 已开始生成后断流                                    | 保留草稿和已完成断点，停止本次生成，不静默追加续写或整篇重写                     |
| 输出截断                                            | 保留草稿或完整的前序阶段；提示调整额度后重跑失败阶段，不重复发送已知会截断的请求 |
| 密钥、余额、模型名、参数、上下文配置错误            | 明确给出修正方向，配置未改变时不自动重试                                         |
| 安全拦截、refusal、content_filter、空回复、用户取消 | 不自动重试                                                                       |
| JSON/字段格式错误                                   | 进入有限定向修复，不伪装成网络重试                                               |

建议技术重试试运行上限为每阶段一次、每逻辑回合两次；格式修复另设额度，但所有调用都记入总账。浏览器 fetch/CORS 失败不能证明上游未执行；无上游幂等能力时不承诺只计费一次，也不静默切换服务商。

### F. 让“已经保存、可以恢复”真实可信（P0/P1）

- 为当前断点定义完整 schema，验证 stage 对应字段、saveId、baseVersion 和 inputKey，以及深层结果的基本完整性。
- 损坏断点保留并明确报错，禁止静默当作不存在后重跑。旧格式明确提示不兼容，不添加多版本兼容层。
- 持久化成功后才能更新“已落盘阶段”；IndexedDB 配额不足或事务失败时区分内存结果与持久化结果，提示真实可恢复范围。
- 已完成正文后抽取失败，只恢复抽取/修复；已完成结算后后续失败，不再执行同一笔钱款或物品变更。
- 定义参数生效规则：连接、模型、超时、输出额度可对尚未完成阶段显式更新，并重新做预算预检；已完成产物保持原样。预设、世界书、玩家输入等内容变化须明确选择继续旧断点或清断点重新开始，复用现有重试/重开流程，避免新增面板。
- 部分流式正文若需要持久化，使用草稿语义，不冒充已完成阶段。刷新恢复、重复提交和跨页版本竞争继续遵守现有日志与版本约束。

## 4. 成功率怎么衡量

先在本地诊断与既有 eval 输出中增加阶段信息，不新建远程遥测系统，不额外记录密钥、完整提示词和正文。

建议记录：逻辑回合标识、阶段、provider/model、标准失败类别、原始结束原因、是否草稿/未定稿、断点复用情况、HTTP 实际尝试数、修复次数、输入/输出 token、阶段耗时。错误内容沿用脱敏规则。

指标分开统计：
1. 首次完整成功率：第一次执行就完整输出且可靠提交的正常回合 / 被接受的正常行动。
2. 有限恢复后完整成功率：同一批行动在允许的修复和技术重试后完整提交的比例。
3. 手动断点恢复率：具备有效断点的失败尝试中，手动恢复后完成且未重做已完成阶段的比例。
4. 正文截断、空回复、协议错误、JSON/字段失败、规则未定稿、存储失败分别占比。
5. 安全拦截、主动取消、待大额花费确认、场外问答单独列示，并公布总量和分母；不能通过挪动失败类别美化成功率。
6. P50/P95 耗时、每成功回合的实际请求数和 token；有可信价格配置时再换算费用。

手动续跑和自动重试需关联原逻辑回合，不能简单按新 requestId 视为独立成功。草稿、独立事件部分生效和未定稿不能算完整结算成功；安全拦截的正确处理算异常处理验收通过，不算内容生成成功。

目前不设未经测量的“达到 99%”目标。改造前后使用相同模型、端点、预设、场景和采样规模对比，报告样本量与费用；现有 eval 通过率继续只说明其实际覆盖范围。

## 5. 实施顺序与改动边界

| 阶段 | 工作                                        | 主要位置                                                                   | 交付标准                                                         |
| ---- | ------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 0    | 明确结果分类与基线记录                      | `kernel/ports.ts`、`schemas/turn.ts`、runtime 诊断、既有 eval              | 能区分完整成功、草稿、未定稿及失败阶段，不凭 done 计成功         |
| 1    | 完成原因、截断/断流草稿、超时、真实保存状态 | provider 适配、`narrator/turn.ts`、`runtime/game.ts`、`checkpoints.ts`     | 无结束原因不结算，卡住可结束，已有正文能按规则保留，不虚报已保存 |
| 2    | 各阶段预算、结构化约束、解析与修复子额度    | `narrator/doc.ts`、`block.ts`、`validation.ts`、`turn.ts`、provider/config | 减少格式失败，关键错误可定向修复，开销有界且不改业务事实         |
| 3    | 候选缓存、恢复参数规则、技术重试收拢        | checkpoint、HTTP/relay、runtime、现有失败提示                              | 失败只重做必要阶段，实际请求数受控，重试不会重复结算             |
| 4    | 固定场景对比与实际应用验收                  | `tools/narrator-eval*`、已有用例、浏览器实际操作                           | 输出基线对比、异常验收结果及剩余限制                             |

实施时按主题分批，避免同时大改存档格式、提示词和界面；如调整当前断点结构，当前版本的保存、读取、导出/导入边界及损坏恢复必须一并验收。正式存档导出是否携带未完成断点也要明确，不能暗示本来未导出的内容可恢复。

## 6. 验收清单

利用现有 eval 增加场景数据，结合本地可控响应和浏览器人工操作，不新增 `*.test.ts` 或测试框架。真实模型评测另行安排调用规模和费用；首批实施与验收未发起真实模型调用。
- 正常对话、交易、战斗、移动、新人物出场、长正文、长预设/世界书，以及高思考开销场景。
- 有文字但缺 finish reason、只收到终止标记、没有终止标记、输出上限截断、中文跨块、畸形关键事件字段。
- 连接挂起、长时间无有效事件、持续心跳但无内容、正常长思考、临时限流、余额不足、密钥错误、网关超时。
- JSON 围栏、前后说明、多候选对象、外壳和条目同时错误、ID 错误、非法事件依赖、超修复预算。
- 正文后抽取失败再恢复，抽取候选缓存再修复，改输出额度后恢复，以及预设变化后的显式重新开始。
- IndexedDB 写失败、坏断点、刷新、重复提交、多个页面版本竞争、日志已写但清断点失败、保存后导出/导入重放。
- 安全拦截和空回复不触发自动重试；主动停止可及时终止等待；恢复不重复扣钱、不重复发物品、不改已完成正文和裁决。
- 核对正常场景与异常恢复中的人物口吻、知情边界、玩家控制权、世界因果和长期记忆，避免格式成功却内容退步。
- 每批代码修改后执行 `pnpm typecheck`、`pnpm lint`、`pnpm check-data`，并实际运行应用验收；逐批记录实际完成范围，不把本节清单全部视为已验收。

## 7. 已批准的首批实施范围

先做阶段 0–1 的核心可靠性与基线记录：修正完成判定，统一草稿保存，加入阶段超时并保证保存提示真实。先具备记录真实失败分布的能力，再以相同场景数据决定阶段 2–3 的投入顺序；真实模型对比评测尚未执行。

## 9. 上下文与调用边界修复（2026-11-28）

### 已实现

- 主回合判断、正文、抽取、格式修复及补充任务在请求前核算完整消息、消息外壳、schema 和输出预留；正文按最终叠加写作预设及世界书后的消息核算。必需内容无法容纳时明确报错，补充任务仍沿用非致命失败语义并记录预算原因。
- 未完成正文从 `prepared` 恢复时采用当前连接的窗口与输出上限，重新预检并保存；提示词、采样及配套输出正则使用原断点快照，预设输出上限继续约束本次尝试。已完成正文只继续抽取，不因更换预设或缩小正文窗口而重写。缺少新字段的旧断点明确不兼容。
- Anthropic / Gemini 原生协议遇到对话历史中的 system 消息时，在任何鉴权、缓存或生成请求前明确拒绝；不移动历史消息、不更改 role。需要这类预设或深度世界书的连接须使用支持原消息序列的 OpenAI 兼容协议，或由用户调整条目角色。
- Gemini 半静态 system 前缀使用完整 `systemInstruction`，跳过不适用的显式缓存；纯静态前缀保留缓存。使用缓存出错时先识别安全拦截，只有明确缓存缺失或过期才回退；创建缓存被拦截同样停止，不继续发送完整提示词。字符串 error 也保留独立的上游 code/status，兼容网关 HTTP 200 安全错误外壳。
- POST 网络失败不再自动重发；浏览器公网跨源请求直接走同源无状态转发，本机、内网及同源地址直接请求，消除直连失败后的第二次 POST。GET/HEAD 保留有限网络重试，设置页说明与实际路由一致。
- 私聊、外貌识别、图像提示词、人物解读、模块解读、正文改写及两类内容创作共 8 个辅助调用消费者统一要求非空、自然结束。正文改写达到本地字数上限后继续读取上游，只有自然完成才发送成功事件；既有本地回退仍保留。
- 向量结果独立于 LRU 缓存保留，超过 512 条及并发淘汰不会丢失当前请求结果；缓存无持久化存储时同样限额。旧记忆检索与完整在场人物卡共用在场判定，排除卡片已包含的全部共同记忆，保留场外记忆。
