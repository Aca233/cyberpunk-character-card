**无跑团沙盘方向 · 一致性审查**

2026-11-16｜针对恢复版与提示词工程策划案的基线审查

实施更新：用户确认“改吧”后，本文所列的八组后台冲突已按原界面固定的边界实施。下面的源码证据与“未实施”表述保留为改动前记录，不代表现状；实际完成项、验证与剩余边界见 [沙盘后台清理交付记录](sandbox-cleanup-delivery.md)。

**结论**

存在实质冲突。普通叙事主链已经停用新的骰点与属性门槛，但仍有旧检定兼容路径，以及隐藏数值、固定动作格、等级锁货、切场刷新和不连续的物件状态。只让正文“不提数值”，无法使这些后台规则自动变成自然因果。

上一版策划案的“保持现有状态行为”把限制写得过宽。正确边界是：原界面保持原样；后台规则逐项判断是否符合目标，不能全部原封不动视作最终方案。制作阶段不需要为旧跑团行为保留兼容链。

**判断标准**

| 可以作为世界事实 | 与当前方向冲突的机制 |
| --- | --- |
| 人物有伤、设备损坏、某件工具在谁手里 | 统一属性点决定生命上限、按伤害档扣固定比例 HP |
| 商人有供货、利益顾虑、既往交往和交易条件 | 好感达到 20/40/60 或声望档位才解锁某级货物 |
| 加速义体受设备状态、持续使用和身体负荷影响 | 按稀有度给 2–5 个动作格，换枪/手雷各占一格 |
| NPC 请求帮忙，玩家可以接下、拒绝或放弃 | 自动按任务结局发固定声望/好感、任务到期强行暂停时间 |
| 未知人物初次出现时抽样补足合理细节 | 开战重抽已有 NPC 的携带物，下一架无故清空旧遗留物 |
| 时间、付款、交付与所有权的事实保持一致 | 每场次数、切场补给、等级或配额作为自由行动的通行证 |

随机数本身、内部版本号、token 预算和请求批次都不是跑团。审核的是它们是否无视世界内的条件来决定玩家行为与结果。“自由行动”也不等于要求任何宣告必然成功；没有接口的主机不能无线入侵，缺少设备的能力不能凭空使用。

此前用户选择过取消数值与资源限制，因此本案不默认保留精确余额、固定价目和容量配额构成的资源经营玩法。可以记录欠款、物件与交易结果；需要多精确的经济模拟仍须在实施设计中明确，本轮不擅自选择、更不删除现有数据。

**一、普通流程已停用骰点，但旧路径没有撤干净**

新选项使用不含 `gate/check` 的 `ChoiceProposalSchema`，普通生成结果明确返回 `check/rolled/gate: undefined`。因此不能说“现在每次普通行动还在掷骰”。

不过请求结构仍接受 `confirm/matrix`。当旧日志确实存在对应检定时，服务端仍会找到它、调用 `rollFaces` 并推送掷骰结果；已掷未确认还会阻止普通行动、直接操作和手机私信。

建议将旧检定提交、确认、属性门槛和阻塞逻辑列为后台清理项；不为它们重新改 UI 或增加新按钮。

证据：`packages/core/src/narrator/block.ts:36`、`narrator/turn.ts:1293`、`schemas/turn.ts:55`、`apps/server/src/game.ts:394`、`:433`、`:481`、`:543`、`:587`。这些旧调用有对应记录这一前提，并非任意提交都能掷骰。

**二、表面写伤势，底层仍保留 HP、属性和人性点**

角色初始化仍按有效肉体属性计算生命上限。伤害按档位扣生命上限的固定百分比，再把剩余 HP 映射成伤势标签。声望升级已经不再发属性点，但旧属性点消费接口仍存在，不能误报为“现在还会正常升级发点”。

义体安装累计人性成本，加速义体连续使用按次数递增扣人性。神经状态的提示还会根据固定人性分段变化。这些仍属于数值结算，不能仅把数值名称改成“身体状况”就算取消。

建议的目标表达：记录具体损伤、影响部位、设备状态、诱因和恢复条件；能力来自已确认的经历与设备，神经负荷来自实际使用和处境。精确替换模型属于后台设计，不能在提示词里宣布不存在而让代码继续扣分。

证据：`systems/character/apply.ts:50`、`:78`、`:107`；`systems/health/apply.ts:79`、`:302`；`systems/cyberware/apply.ts:112`、`:229`；`systems/humanity/prompt.ts:5`。上述 `systems/` 路径均位于 `packages/core/src/`。

**三、仍有固定动作格与场景配额**

斯安威斯坦按稀有度给 2–5 个动作格，提示词明确“快速破解、换武器、扔手雷各占一格”。判断模型还可以在玩家未点名时主动开启，之后真正扣人性。

此外，每段过往只能闪回一次、最多三个输入轮次；这也是人为叙事配额，并非世界中的物理条件。

建议保留加速能力和回忆功能，撤销固定动作配额、按交互次数切断回忆的目标设计。主动使用设备以玩家意图为依据，硬件自动反应需要已确定的设备设定。此处只是提出清理目标，当前代码未改。

证据：`systems/cyberware/schema.ts:113`、`narrator/prompts/context.ts:293`、`narrator/turn.ts:599`、`:1098`；`systems/character/flashback.ts:28`、`:67`、`systems/character/schema.ts:42`。

**四、切场景会凭空补给，还会清掉现场信息**

`scene.end` 和 `rest` 都会回满快捷治疗品、手雷的使用次数。现场危机系统在收场时清除增援 ETA、弱点、扫描与已瘫痪硬件记录。这种场景重置与持续存在的世界不一致。

目标应是：补给有补给来源，设备修复有修复过程；镜头切换只影响展示和上下文选取。临时界面信息可以收起，已经确认的设备损坏等事实不能因收场就消失。

证据：`systems/inventory/index.ts:90`、`:93`、`systems/inventory/apply.ts:243`；`systems/tension/index.ts:56`。

**五、购物与人际关系仍被等级、固定分数控制**

商店和义体医生调用 `rarityLock`，按声望或好感阈值锁货；购买操作实际执行拒绝。委托结局固定改变好感，例如干净完成 +5、失败 −5；声望按风险档位自动增加。用定性中文包装门槛，并没有取消门槛本身。

目标应依据商人是否有货、是否认识玩家、有没有可信引荐、交易风险和真实利益回应。关系是经历和立场的结果，不能只用累计分数解锁合作。委托可以保留为人物之间的请求与约定，不应该强制成为全世界的任务奖励循环。

证据：`systems/economy/schema.ts:21`、`:45`；`systems/inventory/apply.ts:343`、`systems/inventory/actions.ts:97`；`systems/cyberware/apply.ts:90`、`systems/cyberware/actions.ts:112`；`systems/jobs/apply.ts:35`、`:200`。

**六、目录限制和战利品生成阻碍事物持续存在**

物品提示词明确规定目录外东西只能写正文，不能发 `item` 指令，结算也会拒绝未知物品 ID。玩家拿到自制工具、特殊信物等新物件时，当前没有据此保证其进入持久物品状态的通路。

开战时又会按敌人类型和档位随机生成携带物，即使该人物已有卡；下一场战斗清空上一场未捡的物品。战斗中普通 `item gain` 被拒，只允许从倒下的人身上走 `combat loot`，桌上的工具等其他来源受到限制。

目标应让物件拥有稳定身份、来源、位置和归属，交易、丢弃、拾取只是改变这些事实。2077 物品资料可以作为初始模板，不能作为存在资格白名单。首次生成未知细节可以受约束地抽样，已确定的人物财物不能每次开战重抽。

按需缩减目录只能省 token，不能单独解决动态物件持久化。此项需要后台数据与操作语义设计，不应对用户承诺只改几句提示词就完成。

证据：`systems/inventory/prompt.ts:37`、`systems/inventory/apply.ts:108`；`systems/combat/apply.ts:64`、`:136`、`:141`；`narrator/turn.ts:1004`。

**七、增援存在缺少前因的默认触发**

现场暴露状态进入 `openConflict`，若没有已有 ETA，就自动设为四分钟；倒计时到零时，状态文本直接说增援或巡逻力量已到附近。这条默认路径不要求已经有人报警、附近确有人员或路线可达。

目标应先存在通信、目击者、警报系统或巡逻路线，再推导谁会响应、何时能到。屏蔽通信、控制目击者和封锁道路应能改变后果，不能用固定计时器强行制造紧张。

证据：`systems/tension/apply.ts:24`、`:65`；命令接入与计时见 `systems/tension/index.ts:31`、`:65`。

**八、时间推进仍依赖收场和任务节点**

场外推演在场景未变时直接返回不执行。长时间跳跃会被截在最早的期限或委托到期处；玩家明确选择不管某项约定，也可能被节点强行停住。这会让世界运行服从叙事场次和任务流程。

目标是按游戏时间、已定计划和相关事件推进，允许未处理事项自然逾期；角色能感知、且实际会中断行动的事件才需要打断。内部仍可以按批次处理、只计算与当前变化有关的对象，不需要对全城逐个持续调用模型。

证据：`narrator/offscreen.ts:101`、`narrator/stages.ts:185`、`narrator/turn.ts:1013`。

**九、策划案已同步纠正的内容**

- 将“保留现有状态行为”改成“原界面固定，旧规则逐项审查”，避免把去跑团目标排除在方案之外。
- 明确三步调用是内部处理流程，不能成为玩家轮流行动或强制检定的玩法。
- 明确“世界时间与事件驱动”和“按现实时间常驻运行”是两件事；自主世界不强制后者。
- 明确动态物品目前存在底层缺口，不能靠减少提示目录解决。
- 验收增加切场无补给、物件跨场景存在、真实引荐可改变交易、主动忽略约定可自然逾期；旧版冲突行为不作为正确答案。
- 保留事实一致性和稳定保存的要求，撤掉对旧结算规则的默认认可。当前只是规划这些改动，没有执行。

**十、建议的清理顺序**

| 优先级 | 后续工作包 | 验收重点 |
| --- | --- | --- |
| P0 | 明确规则边界、清理旧检定接口及锁定流程；纠正仍向模型灌输动作格、配额和固定门槛的内容 | 普通自由输入不被旧检定锁住；不能提示词说取消、后台仍按旧规则收费 |
| P1 | 切场重置、无前因增援、物件来源和持续存在 | 镜头变化不凭空创造或消灭物件与现场事实 |
| P1 | 伤势/神经负荷表达、交易与人物关系、游戏时间推进 | 结果能追溯到已有条件与发生的事件，符合已确认的无数值资源限制方向 |
| P2 | 在上述规则目标明确后压缩上下文、减少调用、优化缓存 | 不把废弃机制压缩后继续传给模型；质量与成本分别验收 |

提示词去重、目录裁剪和用量测量可以先做，但不能把这些性能改善当成无跑团沙盘已完成。清理后台时保持原界面，必要的数据表达变化先给出具体影响设计，制作阶段不新增旧格式兼容负担。

本次结论来自源码路径审查与已有纯内存检查，不是一次完整游戏实测。未运行真实模型调用，未修改 UI、运行代码、存档或模型配置。
