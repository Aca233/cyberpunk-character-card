用户最新优先级：**正文质量高于调用次数和 token 节省**。人物信息、原文连续性和未兑现约定不得为了压缩请求而随意删除；必要时保留补充请求。正常收场现在仍是三次调用，合并摘要不合格时恢复为四次；触发场外推演另加一次。

用户最新文风约定：**文笔交给预设**。启用预设时，后台不再追加默认文风、篇幅节奏、好坏示例、感官描写配额或重复修辞提醒。内置提示词负责世界事实、玩家权限、人物身份、知情边界与输出协议；人物卡上的具体口吻、经历与台词样本继续作为角色资料。未启用预设时才使用默认表达层，不修改用户导入的预设。

本案以你刚确认基本没问题的恢复版为基线。目标是让人物更可信、世界变化更有因果、长线剧情更连贯，同时降低模型调用与 token 开销。保留自由输入和 2077 的世界特色。

**零、先校准方向：界面保留，旧规则不能默认继承**

目标是玩家扮演角色、通过自然语言自由行动，人物与世界根据已有条件持续变化。骰点、属性门槛、固定行动格、等级解锁、切场景刷新物资和任务强制暂停，都不能因为界面已经恢复就被视为最终设计。

不在正文报数值，并不等于取消了数值玩法。伤势、装备功能、物件归属、债务、承诺、时间和人物知情范围可以作为世界事实保存；HP 百分比、人性点扣费、好感阈值和每场次数是否继续决定结果，必须单独审查。结合此前取消数值与资源限制的要求，本案不再默认保留这些机械限制，也不默认把严格余额与固定价目当成所有交易的唯一解法。精确经济模拟的程度列为待定设计项，本轮不改。

“判断”应解释条件与因果，不能换个名称继续做成功率判定；“抽取/记账”应保证已经发生的事实持续存在，不能等同于照抄旧 RPG 结算。文中的一次“回合”仅指一次输入处理，不代表人物轮流行动或固定动作额度。

世界自主变化不要求模型每秒运行。可以随游戏时间推进或相关事件触发，按已有前因补算必要变化；玩家明确放弃或忽略某个约定时，世界应继续并产生后果。固定地图、已有 NPC 与 2077 资料可作为初始条件，但目录不能成为世界只能存在这些事物的白名单。

本轮发现的具体冲突、实际触发路径与清理优先级见 [沙盘方向一致性审查](sandbox-design-conflict-audit.md)。以下性能优化必须服从这些方向，不以完整复刻旧规则作为质量标准。

**一、范围先固定：原来的界面不动**

局内外布局、样式、人物/义体/物品/消息等展开面板、快捷键和操作入口全部保持原样。本轮只交付这份策划案。

本案的提示词优化工作包不改 `apps/web` 文件和当前公开接口；分类、压缩和材料选择在后台完成，调试数据写开发日志或离线报告。这个范围约束不表示所有旧后台规则和存档字段都必须永久保留。与目标冲突的后台机制列为独立工作包，先设计再实施；若需要调整数据表达，须明确怎样保持原面板正常工作，不能借此重做界面，也不能为保住旧接口额外建立长期兼容层。

| 纳入本案 | 单独立项，不混入本案 |
| --- | --- |
| 系统提示词、阶段职责、人物口吻、事实与知情边界 | 更换整套游戏引擎、重做战斗或经济规则 |
| 各阶段上下文选择、记忆检索、预设预算 | 删除现有功能、重做 UI、改角色创建流程 |
| 调用统计、有限修复、经验证的轻量路径 | 新的存档结构、按现实时间持续运行的世界服务 |
| 冲突规则审查、利用现有状态改善因果表现 | 已确认冲突规则的实际清理与必要状态调整；须先给出实施设计 |

“制作阶段不做历史兼容”继续有效。旧检定 API、锁定流程及兼容字段不能成为永久保留项；本次只是先完成审查与方案，不借机改代码。原界面保持原样与后台去除跑团机制，是两条分别验收的要求。

**二、目前是什么样，先保留哪些已有能力**

当前普通行动的流程是：

```text
玩家输入
  → 判断：理解意图、回忆相关旧事、判断条件与风险
  → 正文：写人物和环境的反应，流式显示
  → 抽取：把已经发生的变化交给代码校验、记账
  → 必要时：场外推演、场景摘要
```

正常情况下，前三步分别调用模型一次。上下文拼装和本地规则校验不调用模型。

| 情况 | 当前调用次数，未计格式修复 |
| --- | ---: |
| 普通行动 | 3 |
| 行动后场景收尾 | 4 |
| 收场且触发场外推演 | 5 |
| 判断识别为场外提问 | 2 |
| 请求已明确标为场外提问 | 1；这是现有内部路径，不新增按钮 |

当前已经有分层提示词、规则模块选择、记忆检索、场景摘要、人物近况、场外事件、流式正文和结构化记账。手机私信另有轻量流程。本案在这些能力上优化，不重新造一套框架。

场外推演目前需先收场，再检查场次、到期事项或时间间隔；这是现状描述，不是推荐的最终调度规则。面向沙盘应优先依据游戏时间、事件依赖和人物行动推进，并允许明确放弃的约定自然逾期。是否按现实时间持续运行是另一个需求，不能与世界自主性混为一谈。提示词能改进推演质量，具体触发规则仍需要后台调整。

**三、已经找到的主要问题**

下面把代码事实和待验证的质量风险分开。

| 问题 | 已核对的事实 | 改进方向 |
| --- | --- | --- |
| 抽取读了太多无关材料 | 抽取会附物品、义体、转折素材、委托模板和后果参考表，并再次读取局面 | 只提供本轮事实证据、相关对象和允许变化的字段 |
| 总预算不完整 | 正文先算预算，之后才注入酒馆预设；判断、抽取等步骤没有同等预算流程 | 按实际最终请求、实际调用模型逐步限额 |
| 修复调用可能膨胀 | 格式错误可以按条目分别触发修复，不是每轮最多一次 | 同阶段错误集中处理，整轮设置修复总额 |
| 守则重复，职责有交叉 | 视角、玩家控制权等规则在多个地方重述；抽取既记事实，也要求补齐新 NPC 秘密和装备 | 统一规则来源，明确已发生、未发生、后台设定和角色已知 |
| 文风容易趋同 | 正文提示同时强调五感、微动作、街头糙话和大量禁用表达 | 人物身份、关系与当前目的优先，环境描写按需要出现 |
| 长场景记忆可能遗漏 | 场景摘要只读取本场末 16 轮，每轮最多取前 800 字 | 保住早期承诺、关键物件与未解决事项，不继续简单砍历史 |

其中“人物趋同、描写机械、补设定泄露”等是根据提示词发现的风险，尚未通过真实模型对照证实，不能当成已经发生的线上故障。

本轮做了一个不调用模型的本地样本：初始世界、完整默认内容表、没有历史、没有酒馆预设，输入“我看看四周”。直接拼装三个阶段的提示词，使用项目现有估算函数得到：

| 阶段 | 粗估输入 token |
| --- | ---: |
| 判断 | 7,564 |
| 正文 | 11,379 |
| 抽取 | 38,846 |
| 三次合计 | 57,789 |

抽取中的物品表约 10,583，义体表约 9,118；两张表合计约 19,701。抽取固定规则约 2,556。因此优先缩减无关目录，收益比单纯压短正文更有依据。

这些是构建函数样本的粗估值，不是实际请求计费，不含模型输出、请求结构开销、原生输出格式开销和真实回合的后续处理。汉字按约一个 token 估算也不等于具体模型分词。它用于定位开销，不能据此宣布实际省了多少钱。

**四、总体做法：先让每一步只读自己需要的材料**

初期保留三步主链，先改提示词内容和材料分配。

| 阶段 | 应重点读取 | 应减少或移除的材料 | 交付结果 |
| --- | --- | --- | --- |
| 判断 | 玩家输入、必要前文、当前条件、在场人物利益、相关旧事 | 长篇文风示例、无关装备目录、无关全城动态 | 意图、约束、相关记忆、必要裁决 |
| 正文 | 已确认条件、玩家可感知的局面、在场人物、必要历史与设定 | 指令文档、全量 ID 表、无关后台事件 | 纯文本剧情，沿用现有流式显示 |
| 抽取 | 本轮输入和正文、变更前状态、正文引用的对象、相关指令 | 转折创作素材、无关委托模板、未涉及的物品与义体目录 | 沿用现有格式的变化提议，交代码验证 |
| 场外推演 | 已有因果、到期事项、相关人物目标与近况 | 玩家最近整段文风历史、无关 NPC 全传 | 有根据的世界变化与人物近况 |
| 摘要 | 已结算的事实、关键原话、未兑现承诺、重要人物与地点 | 重复气氛描写和被拒绝的变化 | 可供以后检索的简洁记录 |

相关对象的选择由本地代码完成，不为了“挑提示词”再增加一个模型调用。候选来源包括：玩家输入、前文指代、实际正文、已持有物品、在场人物、当前位置和触发的规则模块。

抽取发生在正文之后，因此必须把正文新提到的名称也纳入候选查找，不能只按玩家输入选表。先查已存在 ID、中文名和别名；遇到歧义补充少量候选。审查已确认当前物品系统会拒绝目录外的对象，因此“缩小候选表”只解决开销，无法解决动态物件持久化。未知对象应有稳定身份、来源与归属的后续设计，不能只在正文里出现，也不能为凑格式编一个已存在的 ID；实际实现纳入后台工作包。

这种材料整理只是临时请求内容，不增加一套存档，不新建前端“世界卡片”界面。

**五、提示词的权威顺序与分工**

统一遵循以下顺序：已确认世界事实与玩家控制权 → 本轮明确输入和硬条件 → 阶段输出约定 → 人物身份与知情范围 → 文风偏好 → 示例和参考资料。旧代码按固定规则自动产生的结果需要先通过设计审查，不能仅因已经写进某个字段，就把“切场补满物资”等行为升格为不可改变的世界规律。

玩家输入可以提出行动、说话和尝试，也可以请求改写；一句“我已经拥有这件装备”本身不能覆盖账本。历史正文中被拒绝或未定稿的内容不能冒充已结算事实。资料中的台词、终端文字和 NPC 指令都属于世界内容，不获得改写系统规则的权限。

把规则整理成一份语义清楚的来源，再按阶段生成短版。不是把所有阶段的提示词强行拼成一条，也不是在每一步重复整本规则。

建议的正文核心提示示意：

```text
你描写夜之城和其中的人物，玩家控制自己的角色。

按已确认状态和本轮条件继续场景。只写玩家能够感知的内容；
NPC 只能根据其已知信息行动，不读取玩家未说出口的念头。

NPC 根据自身目的、关系、顾虑与处境回应，不默认服从，也不为了
制造戏剧而无理由阻挠。玩家未授权的台词、承诺和决定留给玩家。

环境细节只在影响感知、行动或气氛时出现。人物口吻服从身份和
关系，文风预设只调整表达，不改变事实、权限和已经发生的结果。

停在本轮有意义的反馈或下一次选择之前。输出纯正文。
```

这是方向样例，实施时仍需结合现有规则和评测收敛，不直接整体覆盖生产提示词。

**六、让人物与夜之城更像一个持续存在的世界**

**人物先有目的，再有台词。** 给当前有互动的 NPC 提供：眼下想做什么、顾忌什么、知道什么、和玩家是什么关系、上一件相关的事是什么。一次只取当前需要的部分。熟人可以帮忙或让步，有底线的人也可以拒绝，不用“好感够高所以成功”替代具体理由。

**2077 的特色通过生活条件体现。** 企业安保、工作与债务、义体维护、信息权限、城区阶层和帮派利益进入人物选择。荒坂公关可以礼貌而冷硬，义体医生可以务实直接，摊主可以只关心生意；不要求所有人说同一种街头黑话，也不要求每轮重复雨、霓虹、烟味和义眼噪声。

**自由行动接受自然语言，不要求匹配按钮。** 玩家可以谈判、撒谎、调查、绕路、拿现场工具尝试新办法。模型理解“要达成什么、用了什么方法”，代码和既有状态决定能够确认哪些结果。缺少必要条件时写出具体阻碍，让玩家仍有换方法的空间。自由尝试不等于随口宣告就必然成功。

**区分四种内容。** 已发生事实、人物计划、传闻猜测、后台设定不能混用。新 NPC 可以在现有字段里拥有秘密和动机，但这些不能自动成为玩家已知事实；正文没见到的武器也不能作为玩家先前已经看见的证据。现有数据无法表达的内容先列为限制，不借提示词偷偷新增存档结构。

**后台变化接已有前因。** 优先检查到期约定、未完成交易、人物近况和势力行动，再决定有没有新动静；允许某次没有实质变化。人物可以过自己的生活，不必每件事都围着玩家，也不靠不停生成灾难证明世界在运转。

例如玩家欠修理工一笔配件钱、约好明晚支付，然后去别处待了一天：后续应依据原约定与修理工处境，可能出现催款、暂停交货或关系变化。玩家通过消息或见面得知结果。不能没有前因就宣布“修理工被公司灭口”，也不能在纯叙述中把欠款写成已经还清。

当前“未点名也可能自动开斯安威斯坦”与玩家决定权存在边界冲突；固定动作格与人性点扣费也需要审查。目标保留设备的加速能力及真实负荷，主动使用需符合玩家明确意图，硬件自动反应需有事先确定的设备设定。实际清理纳入后台工作包，本轮不改触发逻辑。

**七、怎样省 token，同时保住剧情质量**

按收益与风险排序：

1. **抽取目录按需提供。** 先去掉无关的大表和创作素材，再精简重复的指令说明；保留关联支付、交付、伤害与时间等必要证据。
2. **按阶段分配状态。** 具体钱物状态给需要核验的阶段；人物表达材料给正文；其他地区的秘密行动留在后台推演。不会因为材料被裁掉就把事实当不存在。
3. **预设注入后再计算总预算。** 将宏展开、检索结果、历史、输出格式说明、回复额度和安全余量一起计入。判断与抽取按各自实际模型窗口计算，不能沿用正文模型的窗口。
4. **记忆先去重，再压缩。** 已经放入最近原文的事件不再大段复述；保留相关承诺、地点、人情、物件归属和关键原话。长期事实与最新状态冲突时以有效结算和时间先后为依据。
5. **固定规则稳定排列。** 稳定的规则和文风放在前面，随轮变化的输入、状态与宏结果放在后面。本地固定模板按提示词与模型方案版本缓存；本地动态材料按状态和相关数据版本失效，避免复用过期信息。每轮变化的状态版本不写进发送给模型的固定前缀，保持服务商前缀缓存的复用条件。
6. **正文长度服从场景。** 短问答可以简短，重要冲突可以展开。不能靠砍掉剧情或破坏用户预设来伪造省 token 的成果。

上下文窗口是容纳上限，不是每轮必须填满的额度。为判断、正文、抽取、推演、摘要分别设置软预算和硬上限；超额先删无关目录与重复内容，再缩减可恢复的历史。关键事实和输出空间不足时沿用现有失败提示，不带着缺失的关键条件盲写。

本地缓存主要减少重复拼装耗时；服务商提示缓存是否降低账单，要以实际能力和返回用量为准。缓存命中也不意味着上下文占用消失。当前用量结构只有输入/输出统计，不能声称已经测得缓存节省。

第一阶段在同一套场景上的暂定目标：**整轮总输入 token 中位数至少降低 20%，争取 30%–50%**，同时不降低事实与记账质量。目标需要实测，不能把上面的单个空历史样本当成所有存档的平均表现。

**八、怎样减少调用次数**

先处理无价值的额外调用，再讨论减少主链。

**第一步：限制修复膨胀。** 本地先做不改变意思的格式处理；同一阶段可以合并的格式问题一次提交。暂定每个普通回合最多额外两次修复，每阶段最多一次；统计上包含这些请求。业务规则拒绝不是格式错误，不能让模型反复改到“通过”为止。关键状态无法可靠结算时，沿用现有未定稿/重生成处理，不写假账。附属摘要或推演失败按现有恢复机制处理，不拖着主回合无限重试。

**第二步：只对能证明简单的情况试验两次路径。** 本地确认无需独立裁决时，可试验“正文 → 抽取”。判断依据同时包括当前局面、相关前文、输入含义和未完成事项；不能看字数，也不能只匹配“聊聊”“看看”。

| 输入情形 | 候选处理 |
| --- | --- |
| 无冲突、无待决交易或承诺的明确普通观察、日常问候 | 经场景集验证后可尝试两次路径 |
| “我答应了”“就那把”“明天再说” | 有指代、承诺或时间歧义，保留完整判断 |
| 买卖、说服、潜入、开火、入侵、受伤、跨时间行动 | 保留完整判断 |
| 场外问现状或可行性 | 复用现有场外路径，不新增界面模式 |

两次路径仍保留抽取。对话也会改变人物认知和关系，不能因为“没有打架”就跳过状态维护。若后续发现轻量路径产生了未经支持的关键变化，本轮不落库，沿用现有失败处理；不偷偷续跑多次、覆盖已流出的正文，再宣称只用了两次。

假设有比例 p 的普通行动可靠进入两次路径，主链平均调用数才会从 3 降为 `3 − p`。实际总数还要加上摘要、推演、修复和失败重试。不能提前承诺每轮都只需一次。

**第三步：摘要合并只作为后续实验。** 可以评估让收场抽取携带简短摘要，但摘要只能记录最终结算成功的事实。先解决摘要与被拒绝变化的对应关系，再考虑省掉单独调用。正文、裁决和记账一次性混合输出不列为首选方案，以免影响流式显示、事实一致性与故障定位。

**九、验收怎么做**

先固定 40 个代表性场景，旧版与候选版使用相同的状态切片、模型方案、采样设置和预设。正式对照每个场景至少重复三次，减少单次随机结果的误导。先跑不调用模型的构建和规则检查；在线对照作为后续实施验收，不在本次策划中执行。

| 场景 | 必须达到的表现 |
| --- | --- |
| 玩家心想对方撒谎，同时问“昨晚你在哪？” | NPC 不听到内心话；不替玩家决定信不信 |
| 同一个问题问摊主、企业公关、义体医生 | 口吻和顾虑各异，不是全员黑话或统一客套 |
| 没装螳螂刀却要求弹刀，随后改拿现场工具 | 先响应实际条件，再理解新方案，不因缺少固定选项拒绝尝试 |
| 计划买枪、实际付款但未交货、交易成功 | 三种情况分别记账；不漏付钱，不凭计划发装备 |
| 新 NPC 有秘密身份，玩家只见到假名 | 后台设定与玩家知情隔离，后续反转有依据 |
| 短输入“就那把”“我答应了” | 找到前文对象，不被轻率划入无状态变化的闲聊 |
| 长场景早期承诺、旧人重逢 | 能召回关键事实，不因摘要截断改口 |
| 明确睡六小时且不赴约，跨过已知约定时间 | 约定可以自然逾期并发生后果；不因任务节点强行暂停。门外有人实际闯入等现场事件则可合理打断 |
| 切场景、再开战、返回旧现场 | 不凭切场补药补雷，不重抽已确定装备，不无故清掉遗留物 |
| 同一角色低声望但有真实引荐，进入商店 | 按人物已知、供应与交易条件回应，不只按数值阈值锁货 |
| 玩家获得有明确来源的自制物件 | 能跨轮保留身份、位置和归属；目录外不能自动等于不存在 |
| 超长预设、普通预设、无预设 | 最终请求预算有效，预设不改写状态和玩家权限 |
| 一次响应中多个 JSON 条目出错 | 修复请求有界，关联的支付/交付等变更保持一致 |

建议指标与门槛：

- **界面：** `apps/web` 文件与确认基线内容一致；公开返回结构不变，原面板可正常读取。
- **设计一致性：** 新增的无跑团与世界连续性用例必须符合目标。旧版已经违背目标的行为记录为待解决基线问题，不把“与旧版一致”误当通过。
- **事实与控制权：** 专门用例中玩家越权、隐藏信息泄漏、无依据记账零新增失败；发现一次就不能通过该项。
- **记忆：** 有标准答案的关键事实召回率不得低于基线；“不记得”与“编造记忆”分别统计。
- **文风：** 人物差异、节奏、因果自然度做匿名成对比较，至少保持基线；不能只凭禁词变少判定更好。
- **成本：** 每阶段分别记录请求数、输入/输出 token、修复次数、失败次数；比较整轮中位数与 P90。达到输入 token 降幅目标后，仍需单独核对实际费用。
- **延迟：** 分开统计首段正文出现时间、正文完成时间和状态结算完成时间，不能把等待藏到结算阶段。
- **可靠性：** 未定稿率、关键变化丢弃率不得恶化；低风险路径的误判必须单列。

全部请求的实际费用应按各模型的未缓存输入、已缓存输入、输出及服务商其他计费项分别求和。少一次便宜辅助调用，不一定比减少大量主模型输入更省钱。

**十、实施顺序与停止条件**

| 阶段 | 具体工作 | 交付与进入下一阶段的条件 |
| --- | --- | --- |
| 0：方向审查 | 区分无跑团目标、世界事实、旧规则和兼容残留，列出后台冲突工作包 | 当前已完成静态审查；不把 UI 固定误写成后台规则全部冻结 |
| A：建基线 | 固定场景、记录各阶段材料大小、调用与失败情况，保存前端哈希 | 可复现的对照报告，不改产品行为 |
| B：提示词整理 | 去重、明确权威顺序、改善人物口吻，隔离事实/计划/秘密 | 关键质量用例不回归，仍保持三次主链 |
| C：上下文减负 | 相关目录、阶段材料选择、最终请求预算、预设前缀、有限修复 | 成本目标达标，记忆和结算质量不降低 |
| D：调用实验 | 小范围评估两次路径，必要时评估摘要合并 | 只有经对照证明有收益的路径进入正常运行 |

在 A–D 的提示词工作包中，发现界面文件或公开接口变化、关键事实质量下降，应停止扩大范围，先处理该阶段问题。另列的后台冲突清理工作包须有自己的接口影响与验收设计；它不是顺手重写前端的理由。

**十二、本案建议先批准的工作包**

阶段 0 已发现后台冲突。接下来先把清理范围写清，再实施 A、B、C：建立基线、整理提示词、减少无关上下文、补齐全链预算和修复上限。提示词包保留三步处理结构和原界面，不再承诺永久保留所有现有状态行为。对底层冲突未处理的部分如实标为限制，不能只优化文案就宣布沙盘完成。

拿到质量与成本对照结果后，再决定是否进入 D。后台清理按附属审查列明的范围另写实施设计，不扩大成全引擎重构；按现实时间持续运行仍是独立需求。
